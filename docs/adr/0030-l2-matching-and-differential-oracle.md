# ADR 0030: L2 Quote/Tick Matching and Differential Oracle

Date: 2026-10-14. Status: **accepted** (2026-10-14). Roadmap stories: E3-S1b, E3-S1d. Supersedes ADR 0025 decisions 1–3 for scheduling purposes; ADR 0025 decisions 4–5 remain in force.

## Context

ADR 0025 (2026-10-13, accepted) deferred E3-S1b and E3-S1d because no canonical tick/depth tape existed and the default simulator was L1 (bars only). The decision required a follow-up ADR to define "the tick event stream (QuoteTick/TradeTick/Depth delta), time granularity (ns), book construction, and the conformance vector format" before scheduling.

Since then the code inventory shows:

- `QuoteTick`/`TradeTick`/`AggressorSide` already exist with `UnixNanos` timestamps (`crates/honba-messages/src/market_data/tick.rs:44,195`).
- They are wire `Event` variants (`events/event.rs:54,56`) and flow through `MarketEvent::QuoteTick/TradeTick` (`crates/honba-ports/src/connector.rs:32`).
- Deterministic synthetic streams already exist (`honba-testing::VecFeed::quote/trade`, `crates/honba-testing/src/feed.rs:44,60`).
- No multi-level `Depth` event type exists; depth is only a read-port/API response type (`DepthSnapshot`/`DepthLevel` in `honba-ports`/`honba-api`).
- All matching cores are L1: `NextOpenSim` (next-open), `BarFillEngine` (last close), `PaperExecution` (fixed price), `ScriptedExecution` (scripted).

The remaining blocker was the *event-stream contract* for the matcher, not a persistent data tape. This ADR provides that contract so E3-S1b/S1d can be scheduled while preserving ADR 0025 decisions 4–5 (L1 stays canonical reference; no L1 vector changes).

## Decision

### 1. Event stream

**v1 stream = `QuoteTick` (top-of-book) + `TradeTick` (prints). No new wire type.**

- `QuoteTick` fields: `instrument_id`, `bid_price`, `ask_price`, `bid_size`, `ask_size`, `ts_event`, `ts_init` (ns). Represents a top-of-book update.
- `TradeTick` fields: `instrument_id`, `price`, `size`, `aggressor_side`, `trade_id`, `ts_event`, `ts_init` (ns). Represents a market print.
- Optional bounded `DepthSnapshot` **input** (not a streaming delta) may be supplied to the matching core for marketable-order walking. It contains ordered `bids[]`/`asks[]` of `DepthLevel { price, qty }` (existing types from `honba-ports/src/snapshot.rs:31`). This is an opt-in enhancement; the v1 matcher works with QuoteTick only.

**Time granularity:** `UnixNanos` (ns), matching the existing tick types. Event-time only; wall clock is excluded from domain crates (ADR 0016).

### 2. Book construction

Top-of-book `L2Book`: best bid/ask + size per instrument, updated by `QuoteTick` events. **L3 full-book replay remains DROPPED** per ADR 0025 (consequence 5) and `ROADMAP.md` §3.7. No order-book depth deltas are streamed.

### 3. Matching semantics (v1)

| Order type | Fill rule |
|---|---|
| Market | Fill at opposite touch (buy at ask, sell at bid); partial by available top size if `DepthSnapshot` provided |
| Marketable limit | Walk book at current touch; remainder rests (or cancels under IOC) |
| Resting limit | **Fills when a `TradeTick` prints through it** (`buy: trade.price <= limit`; `sell: trade.price >= limit`) |
| Stop / stop-limit | Trigger on `TradeTick` crossing `trigger_price`; then behaves as market/limit |
| IOC | Fill immediately against current book; cancel remainder |
| FOK | Fill all-or-nothing vs current book size; else reject |
| Day | Expire at session close (`MarketProfile`/`ExpiryRules`) |

**Time priority:** FIFO at the top price level. Queue order is the tiebreak (ADR 0019 decision 6). The `depth_survival_discount` stub (`crates/honba-sim/src/latency/mod.rs:90`, currently `1.0`) is wired to quote size for future size-aware partial fills.

**Cancel timing (L2 row per ADR 0019 decision 6):**
- `order_cancel_requested.ts = now` at `cancel()`
- `order_cancelled.ts = now` in v1; later replaced by `LatencyModel` delay at that book position.

### 4. Conformance vectors

New file: `schema/conformance/l2_sim.json`.

Shape mirrors `next_open_sim.json` (`schema/conformance/next_open_sim.json`): `{ fixture_version, type: "L2Sim", description, scenarios: [{ name, chunk, config, steps[], expect: { drains[], final{} } }] }`.

Step ops added: `quote` (QuoteTick), `trade` (TradeTick), alongside existing `bar`, `submit`, `cancel`, `drain`, `advance_ts`.

`expect.drains[]` entries contain the same `[order_id, symbol, side, qty, price, ts, costs_minor]` rows. `expect.final` matches the journal schema.

**Requirement:** `next_open_sim.json` and `order_state.json` are **not modified** (ADR 0025 decision 4). L2 is a separate, opt-in `ExecutionEngine`.

### 5. Differential oracle (E3-S1d)

A **naive reference matcher** (simple, exhaustive, O(n)) and the optimised `L2Sim` run on the same seeded event stream. Property test `oracle_agrees_seeded_streams` asserts identical fills/sequences. Fixture: a recorded seed set (same generator as conformance vectors). This matches the "matching-core study" item in `ROADMAP.md` §3.7.

### 6. Scheduling

E3-S1b split into three chunks (each S–M):
- **E3-S1b-1:** L2 matching core (`honba-sim/src/l2/`), `ExecutionEngine` + `Handler`, seeded `FillModel`/`LatencyModel`, unit tests.
- **E3-S1b-2:** Python parity (`make_simulator(fill="l2")`, native binding via `honba._honba`, fallback reference).
- **E3-S1b-3:** `l2_sim.json` + `gen_l2_vectors.py`; conformance replay (Rust + Python).

E3-S1d (differential oracle) ships after E3-S1b-3.

All work is opt-in; the default simulator and research pipeline remain L1 (ADR 0025 decisions 1–2).

## Consequences

- Removes the scheduling blocker from ADR 0025 without introducing a tick/depth tape.
- L1 behavior stays the canonical reference; L2 vectors are separate.
- Determinism preserved: seeded models, recorded fixtures, no wall clock.
- `DepthSnapshot` input is optional; no new streaming depth wire type.
- Cross-repo impact: new docs page; `on_quote`/`on_trade` hooks already exist in strategy API.

## Open items for code review

- Trade-through vs quote-touch for resting limits: default is trade-through on `TradeTick`; config flag `fill_on_quote_touch` may be added later.
- `depth_survival_discount` wired to quote size for v2 size-aware partials.
- IOC/FOK day-expiry interaction with session rules.

- 2026-10-15: async gateway bridge (E3-S7 open item). `honba_api_rest::GatewayVenue` implements `ExecutionVenue` over any `honba_ports::ExecutionGateway`. **Decision: a command channel to one task that owns the gateway, with events returned through a shared queue, not `block_in_place` or a per-call reply oneshot.** The `ExecutionEngine` calls run under a std mutex inside async handlers: `submit`/`cancel` only enqueue a command on an unbounded channel and return `Ok(())` (never an await, never a block, the lock covers a channel send), and the task's answers (refusals, fills, cancel acknowledgements) are pushed as `ExecutionEvent`s that `drain_events` empties, the path the ledger mapping already uses. Rejected alternatives: `block_in_place` + `Handle::block_on` panics on a current-thread runtime (tests, `#[tokio::test]`) and parks a worker per order; a reply oneshot awaited synchronously is the same blocking in disguise. Consequences: (1) a broker refusal is a `Rejected` event after the fact, so `POST /orders` answers `OK` with row `Submitted` and the row turns `Rejected` on the next drain; `AppState::advance_market` drains (with or without bars) and `AppState::spawn_venue_drain(every)` drains on a timer for a venue with no bar feed. (2) The task translates the gateway's venue id back to the client order id (fills may carry either) and tracks `cum_qty`/`complete` per order for the ledger's `PartiallyFilled`/`Filled`; the fill stream is polled (default 50 ms, `Ok(None)` = idle); a fill for an unknown order is dropped with a warning. (3) A cancel first polls fills, then cancels by venue id; success yields `Cancelled` with the unfilled remainder at the caller's `now`; a refused cancel (already filled) yields no event and the fill stream reconciles it; cancelling an unknown order never reaches the gateway. (4) Error mapping, no new wire codes: `PortError::Rejected` -> `order_rejected`; `Unavailable`/`Retriable`/`Terminal`/`Unrecoverable` -> `order_execution_unavailable`; `Timeout` -> `timeout`; `Transport` -> `transport_error`; `InvalidRequest` -> `validation_invalid_request`; `Unsupported` -> `unsupported`; others -> `internal_error`. The code is the `reason` of the `Rejected` event (`ExecutionEvent::Rejected.reason` allows an `ErrorCode` wire spelling) and is logged; the `Order` ledger row has no reason field, so it is not on the wire. (5) Known gaps: a submit `Timeout`/`Transport` error leaves the venue state unknown but the row becomes `Rejected` (the ledger has no unknown status; reconciliation against broker order books is future work); `modify_order` is not bridged (`ExecutionEngine` has no modify); the unbounded command queue relies on the risk stage's order-rate limit for backpressure; a command still queued when the task dies is lost, later `submit` calls fail with `Component("execution gateway task stopped")` and the row is `Rejected`. - 2026-10-15: ledger rows report fills and rejections (E3-S7 open item). **Decision: widen the `Order` wire row additively instead of adding `/trades` or `/positions` routes.** `Order` (the row `GET /orders` and `POST /orders` return, also the `order` event snapshot) gains three optional fields, each omitted from JSON while unset so an old client parses a new row and a new client parses an old one (ADR 0012 rule 1, same as `product` and `cancel_requested`): `filled_qty` (cumulative, default 0; omitted at 0), `avg_fill_price` (quantity-weighted over the fills the ledger has seen; omitted until a fill) and `reject_reason` (`{code, message}`: the stable `ErrorCode` string and a short message). `Order::validate` checks `0 <= filled_qty <= quantity` and `avg_fill_price > 0`. A `Rejected` event becomes `reject_reason`: a reason that is an `ErrorCode` wire string (the `GatewayVenue` and pre-gate refusals) keeps that code with a stock message, any other text (the simulators' `unsupported_order_type`, `no_position`, `insufficient_funds`) becomes `order_rejected` carrying the text as the message; a `submit` that errors is `order_rejected` with the error text. A row with no fill becomes `Rejected`; a `PartiallyFilled` row keeps its status and records the reason for its refused remainder; a row cancelled after a partial fill keeps `Cancelled` and its `filled_qty`. Python: `LedgerOrder` gains the same three fields (`RejectReason` model); `RestExecutionAdapter` reports the real `filled_quantity` / `average_price` / `"<code>: <message>"` and derives `positions()` with the real average price (rows applied in ledger order through `Position.apply_fill`, partial and part-filled-then-cancelled rows included); `LedgerLimitationError` remains only for an older server, detected as a `filled`/`partially_filled` row with `filled_qty == 0` (`fill_price=` still supplies a price there, a partial always raises). `trades()` stays a `CapabilityError`: a row holds a running average, not a per-fill history, so a trade list cannot be built honestly; a `/trades` route would need a fill log the ledger does not keep. - 2026-10-15: ledger follow-ups, closing the seven known gaps of the ledger fill fields entry. (1) **Risk refusals are recorded, the 422 is unchanged.** ADR 0018 decision 6 already makes a refusal an audited `Rejected` fact on the engine path (`Initialized -> Rejected`, `reason` = the `risk_*` code), and decision 5 only fixes the HTTP rendering, so a `rejected` row with `reject_reason` = `{refusal code, "order refused by risk: <rule>"}` is consistent with both and with every contract test (the 422 body, status and context are untouched; the refusal still never reaches the venue). Only a request that carries a `client_order_id` is recorded: without one the route key is the shared placeholder `rest`, so a recorded refusal would answer every later keyless order with the refusal. `OrderLedger::record_refusal` stores the row and the full `ErrorDetail` (with `context`); a repeat of the id returns that same 422 (`OrderLedger::refusal`), not a 200 row and not a duplicate. The approval-queue path records at approval time when the queued request had a key; `POST /positions/close` generates its own keys and does not record (a retried close would otherwise add a row per attempt). Validation 422s (bad side, missing qty) are not risk refusals and are not rows. Cost: an unbounded stream of distinct refused keys grows the in-memory ledger, like any other key. (2) **Broker text survives.** `GatewayVenue` now puts `<stable code>: <PortError text>` in the `Rejected` event `reason` (a venue refusal reads `RMS: margin`; the Python shim, whose code and message are the same string, is not doubled), cut to 256 characters on a char boundary with a trailing `…`; `exec.rs reject_reason()` splits at the first `: ` when the head parses as an `ErrorCode`, so the ledger code is unchanged and the message is the broker text. A bare code (pre-gate refusals) and any other text (simulator reasons) behave as before. The pyo3 path already carried `str(exception)` into `PortError` (`failure_of` -> `classify`), verified end to end by `test_gateway_server.py`. (3) **`filled_at`.** `Order` gains the optional, additive `filled_at` (`UnixNanos`, omitted until a fill), set by `apply_fill` from the fill's `ts_event` whenever `cum_qty` grows; `RestExecutionAdapter.positions()` applies rows sorted by it (stable) when every filled row has one and keeps ledger order otherwise (older server). A row is one instant (its last fill) however many partials it merges, so a row part-filled before and after another row's fill is still approximated. (4) **Exposure.** `OrderLedger::position()` is now, per row, the filled part plus what may still fill: working rows (`Submitted`, `Accepted`, `PartiallyFilled`) count at full quantity (unchanged, conservative), a `PartiallyFilled` row whose remainder was refused (it carries a `reject_reason`) counts only `filled_qty`, `Cancelled`/`Expired`/`Rejected` rows count `filled_qty` (so a cancelled partial keeps its filled exposure), `Filled` counts the quantity, `Initialized` nothing. Callers: the risk gate (`risk_request`) and `POST /positions/close`; both follow the new rule, so a close now covers the filled part of a cancelled partial. No ADR 0018 rule changes. (5) **Completion and average.** A fill that completes a row (`Filled`) clears `reject_reason` (a filled order was not refused); a reason on a row later cancelled is kept. The average is computed from `cum_qty` deltas: the newly filled quantity (`cum_qty` capped at the order quantity, minus what the row had) is priced at the reporting fill, so a venue whose `cum_qty` disagrees with the sum of fill sizes cannot drift it; the first report the ledger sees with `cum_qty` above its fill books the unseen part at that price; a replayed or stale report (no growth) changes neither quantity, average nor `filled_at`. (6) **Python mirrors.** `honba.wire.wire.Order` (hand-written, not generated; parity pinned by `schema/golden/order.json`, which gained fill/reject cases and two invalid ones, read by the Rust and Python golden tests) and `LedgerOrder` carry `filled_qty`, `avg_fill_price`, `reject_reason` (one `RejectReason` model in `honba.wire.wire`, re-exported by `honba.client.models`) and `filled_at`; the MCP tool schemas do not mirror the row and did not change. `product` is still not modelled in `wire.Order` (unchanged). (7) **Price guard.** The non-finite/non-positive guard in `apply_fill` is reachable (the method is public) and is now covered by `a_fill_with_a_non_finite_or_non_positive_price_or_quantity_is_dropped`. Regenerated: `schema/domain`, `schema/openapi`, the Python `.pyi`, frontend `domain.ts` (the client and honba-docs api-reference had no drift). Additive wire change only (one optional field). Known gaps: the ledger still keeps no per-fill history (so no `/trades`); risk refusals without a `client_order_id` and refused closes are still not rows; the ledger and its refusal map are unbounded in memory.

- 2026-10-16: persistent tick store, the "a Parquet tick store remains open" item. `honba-feed` gains `parquet_ticks`: `tick_schema()` (the column layout, so producers and consumers agree), `write_tick_file(path, quotes, trades)` (quotes first, each kind in input order) and `ParquetTickStore::open(root)` reading `{root}/ticks/*.parquet` in file-name order. **Decision: a flat, self-describing tick file — one Parquet file, a `kind` column (`quote`/`trade`), the columns a row's kind does not use null — read whole at `open`, rather than a date-/instrument-partitioned layout or a range-pushing streaming reader.** Rejected for now: partitioning needs a producer that knows the calendar and buys nothing until ticks are large enough to matter, and a streaming reader would have to read every file anyway because nothing on disk says which file covers which instrument; the reader keeps room for both later (it already merges files in name order). Consequences: (1) the reader does all I/O once, at `open`, like `CatalogInstrumentMaster`, so the store is persistence and a standard columnar interchange, not a memory saving — a run still holds the ticks it matches against. (2) Rows are decoded through the wire type (`serde_json` into `QuoteTick`/`TradeTick`, `try_from = ...`), like the NDJSON loader, so invariants are checked once in `honba-messages` and a bad row is a `TickStoreError::BadRow` naming the file and zero-based row, never a panic (`QuoteTick::new` `debug_assert`s, so it must not be used on untrusted rows). (3) `read_quotes`/`read_trades` keep the port's semantics exactly: sorted by `ts_event` (stable, ties in file then row order), an instrument with no ticks is `Ok(vec![])`, and a store holding no ticks at all answers `PortError::Unsupported` — which is what the `l2_requires_ticks` refusal needs. (4) `honba serve --ticks <FILE|DIR>` now accepts a directory as well as the NDJSON file (`serve::TickSource::{Ndjson, Parquet}`), so the two formats are the same flag and the start-up rule (`l2` needs `--ticks`) is unchanged. (5) `honba data ticks-import --ticks <FILE> --out <DIR>` builds `{out}/ticks/ticks.parquet` from the NDJSON format and reads it back before reporting success, so an unreadable store is a start-up error rather than a later refusal. Known gaps: no partitioning or range push-down, the store is loaded whole at open, ticks are still not journaled and `l2` runs still skip the result cache. No wire or schema change. Tests: `crates/honba-feed/src/tests/parquet_ticks.rs` (roundtrip, half-open range, merge and tie order, empty store unsupported, bad kind/missing column/crossed quote), `crates/honba-api-rest/tests/rest_backtest_l2_parquet.rs` (a `fill_model=l2` run matched against a store read back from disk, and the empty-store refusal), `crates/honba-cli/tests/serve.rs::fill_model_l2_with_a_parquet_tick_store_runs_a_backtest_end_to_end` (`ticks-import` then `serve --ticks <DIR>`).

- 2026-10-16: per-request `fill_model` (the other half of the "the execution config is set at composition, not per request" item). `BacktestRequest` gains an optional `fill_model` (`bar_fill`, `bar_fill_through`, `l2` or `none`) that overrides the server's configured model for that run only. **Decision: put the field on the wire request and pin it in the manifest, rather than adding a second REST route or a server-reconfiguration endpoint.** The manifest is the reproducibility record (ADR 0017), so a run's fill model belongs beside its seed and window; a route would leave the manifest unable to say how a run was filled, and a global switch would race between concurrent runs. Consequences: (1) `honba-api` cannot depend on `honba-config` (layering), so the accepted spellings live in `honba_api::FILL_MODELS` and `honba-api-rest` deserialises the name into `honba_config::FillModel`; a test asserts the two sets are equal. (2) An unset `fill_model` means "use the server's model", so composition still decides the default and nothing changes for an existing client. (3) `ResolvedBacktest` gains `fill_model: Option<String>` with `default` + `skip_serializing_if`, so an old manifest still parses and a new one omits the field when unset: no `MANIFEST_VERSION` bump (ADR 0012 rule 1). (4) An unknown name is a `422 validation_invalid_request` with `context.field = "fill_model"` at submit, through the existing `resolve`, not a failed run. (5) The executor resolves the effective model once and uses it for the cost-model version, the cache on/off decision and the venue; a `bar_fill` request on an `l2` server runs off bars, and an `l2` request on a `bar_fill` server matches ticks and carries the same `l2_requires_ticks` refusal when there is no source. (6) `bar_fill_through` and `none` stay `Unsupported` in a run, as the server-level model already did; only the request's validity is checked at submit. No manifest-version or wire-version change. Tests: `crates/honba-api/src/tests/run_requests.rs` (carried, unknown, blank), `crates/honba-api-rest/src/tests/executor.rs` (override both directions, the stable refusal, and `FILL_MODELS` vs the config enum), `crates/honba-api-rest/tests/rest_backtest_l2.rs` (a request `l2` over a bar-fill server, and the unknown-name 422).

### Tick file format (`honba serve --ticks`, version 1)

NDJSON, UTF-8, one JSON object per line; blank lines are ignored. Line 1 is the header `{"honba_ticks":1}` (any other version is refused, so a later format cannot be misread). Every later line is one tick, tagged by `kind`:

```
{"honba_ticks":1}
{"kind":"quote","symbol":"TCS","exchange":"NSE","ts_event":1704067200000000000,"bid_price":99.9,"ask_price":100.1,"bid_size":500,"ask_size":400}
{"kind":"trade","symbol":"TCS","exchange":"NSE","ts_event":1704067200500000000,"price":100.0,"size":50,"aggressor":"buyer","trade_id":"T-1"}
```

- `quote`: `symbol`, `exchange`, `ts_event`, `bid_price`, `ask_price`, `bid_size`, `ask_size`, optional `ts_init`.
- `trade`: `symbol`, `exchange`, `ts_event`, `price`, `size`, `aggressor` (`buyer`, `seller` or `no_aggressor`), `trade_id`, optional `ts_init`.
- `ts_event` / `ts_init` are unix nanoseconds as JSON integers (this is a file format, not the `UnixNanos` wire object); `ts_init` defaults to `ts_event`.
- Unknown fields and unknown `kind` values are errors. Tick invariants are those of `QuoteTick` / `TradeTick` (finite values, sizes `>= 0`, `bid_price <= ask_price`).
- Ticks may appear in any order and any mix of instruments; the reader sorts by `ts_event`, stable for ties. A file with a header but no ticks is refused.
- The whole file is held in memory; the persistent alternative is the Parquet tick store (`--ticks <DIR>`, see below). Implementation: `crates/honba-cli/src/ticks_file.rs`.
